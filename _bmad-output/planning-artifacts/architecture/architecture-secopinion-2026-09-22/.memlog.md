- (decision) AD-1 [ADOPTED]: Modular Monolith paradigm. Binds: all v1 features. Prevents: microservice-complexity overhead at POC stage while still enabling clean future extraction. Rule: single deployable app; internal module boundaries by domain: Patients, Doctors, Cases, Payments, Admin.
- (decision) AD-2 [ADOPTED]: Module isolation rule. Binds: all modules (Patients, Doctors, Cases, Payments, Admin). Prevents: a distributed-monolith future where extracting a module to its own service requires untangling shared tables or hidden internal references - this is what makes later microservice-on-EKS extraction incremental rather than a rewrite. Rule: (1) each module owns its own DB tables; no module may directly SQL-join or query another module's tables - cross-module reads go through that module's exported service function. (2) modules call each other only via explicit exported interfaces (in-process function calls in v1), never by importing another module's internals - this interface is the seam that gets swapped for HTTP/gRPC if/when a module is extracted to its own service.
- (decision) AD-3 [ADOPTED]: Payment provider abstraction. Binds: Payments module (FR-8, FR-12, FR-13). Prevents: gateway-specific (mock or real UPI) code leaking into Cases/Payments business logic. Rule: all payment/payout/refund operations go through a PaymentProvider interface; v1 ships a MockPaymentProvider implementation, v2 swaps in a real UPI gateway adapter behind the same interface without touching calling code.
- (constraint) Deployment target updated: local laptop (Docker Compose: app + Postgres) for initial development, then AWS EKS (Kubernetes) for later deployment - replaces earlier 'unspecified cloud' note. v1 EKS deployment is a single Deployment+Service running the modular monolith container; no per-module services planned for v1 (see AD-1/AD-2 - module extraction is a v2+ option, not a v1 requirement).
- (decision) AD-4 [ADOPTED]: Reference-by-ID rule for cross-module references. Binds: all modules (Patients, Doctors, Cases, Payments, Admin). Prevents: hidden coupling via DB-level foreign keys across module boundaries that would block future per-module database/service extraction (AD-1/AD-2). Rule: cross-module references are stored as plain ID columns only (e.g. Case.patientId, Case.doctorId, Payment.caseId) - no DB-level foreign-key constraints across module table boundaries, even though v1 uses one shared Postgres instance. Referential validity is enforced at the application layer by calling the owning module's exported interface (e.g. DoctorsModule.getVerifiedDoctor(id)), not by a DB constraint. Modules may still use normal FKs within their own owned tables. Tradeoff accepted explicitly: v1 loses DB-enforced integrity for cross-module refs in exchange for keeping the door open to real microservice extraction on EKS without a rewrite.
- (decision) AD-5 [ADOPTED]: Optional doctor selection at Case submission. Binds: Cases module data model (FR-3/FR-9). Prevents: forcing a doctor pick at submission time when the PRD flow allows deferred/unassigned cases. Rule: Case.doctorId is nullable. At submission, patient may optionally browse/search the list of verified doctors (Doctors module, verification-status filtered) and pick one; picking a doctor is not mandatory. If left unassigned, the Case enters a queue for assignment (mechanism TBD - see open question on claim vs admin-assign). Doctor offboarding: a doctor who wants to leave notifies Admin out-of-band; in v1, Admin manually reassigns that doctor's open/in-progress cases to another doctor - Case.doctorId must be admin-mutable after initial assignment, not just settable once.
- (decision) AD-6 [ADOPTED]: Case-to-doctor assignment mechanics. Binds: Cases module (FR-9). Prevents: unbounded assignment race conditions and undefined SLA behavior on reassignment. Rule: (1) Assignment is hybrid pull-or-push, no auto-assignment/specialty-routing in v1 - any verified doctor may browse the open/unassigned-case queue and self-claim a case (atomic claim-if-still-unassigned operation to prevent two doctors claiming the same case); independently, Admin may manually assign or reassign any case to any verified doctor at any time (covers both resolving unassigned cases and offboarding reassignment). (2) Reassignment does NOT reset the Response SLA clock - the clock remains anchored to the Case's original submission timestamp regardless of how many times doctorId changes, since the incoming doctor inherits the case's existing documents/notes/history from where the prior doctor left off.
- (decision) AD-7 [ADOPTED]: Auth and file storage follow the same provider-abstraction pattern as AD-3 (payments). Binds: Patients/Doctors/Admin auth, Cases module document uploads. Prevents: OTP-gateway or storage-backend specifics leaking into business logic; keeps v1-to-v2 swap cheap. Rule: (1) OTP delivery goes through an OtpProvider interface - v1 ships a MockOtpProvider (e.g. fixed/logged OTP, no real SMS send), v2 swaps in a real SMS/OTP gateway behind the same interface. Session/auth mechanism itself (JWT-based sessions for Patient/Doctor/Admin roles) is implemented for real in v1, not stubbed - only the OTP delivery channel is mocked. (2) File/document storage goes through a StorageProvider interface - v1 ships a LocalDiskStorageProvider (documents saved to local disk in dev), v2 swaps in a cloud blob storage adapter (e.g. S3-compatible, given AWS EKS deployment target) behind the same interface without touching Cases module business logic.
- (decision) AD-8 [ADOPTED]: SLA breach detection via daily batch job. Binds: Cases module Response SLA enforcement (FR-13, Refund Pending transition). Prevents: over-engineering a real-time/precise timer system the PRD does not require. Rule: a scheduled job runs once per day (not sub-hour precision) and scans for Cases past the 5-day/120h Response SLA window that are still awaiting an Opinion; matching cases transition to Refund Pending. Exact hour/minute precision is explicitly not required - daily granularity is acceptable per product intent. v1 implementation can be a simple in-process scheduled task (e.g. cron-like scheduler within the monolith); no separate queue/worker infrastructure needed at this scale.
- (decision) AD-9 [ADOPTED]: Consistency conventions. Binds: all modules and code. Prevents: divergent naming/response/error styles across independently-built modules. Rule: source layout is src/modules/<module-name>/ per module (patients, doctors, cases, payments, admin) each owning domain/, service.ts (exported interface per AD-2), repository.ts (module-owned tables only), routes/; shared/ holds OtpProvider, StorageProvider interfaces + mock impls. Naming: TypeScript camelCase vars/functions, PascalCase types/classes/components, kebab-case files/folders; Postgres snake_case tables/columns (Prisma maps to camelCase models). Cross-module calls only via a module's service.ts (never import another module's repository.ts or internal types). API responses use a consistent envelope {data, error} where error is null on success or {code, message} on failure. Domain errors are typed per module and mapped to HTTP status only at the route-handler boundary. All primary keys are UUIDs (not auto-increment ints), consistent with AD-4's reference-by-ID rule and future service extraction. JWT carries userId + role (patient/doctor/admin); role-based access is resolved at the route-handler boundary.

- (decision) AD-10 [ADOPTED]: Batched Doctor Payout via daily job. Binds: Payments module (FR-12). Prevents: synchronous payment-gateway calls on the Case-closure request path and the complexity of real-time disbursal at POC stage. Rule: payout is NOT triggered synchronously when a Doctor submits an Opinion. Instead, a daily scheduled job (same batch pattern as AD-8) scans Cases closed with an Opinion since the last run, calculates each Doctor's Payout share, and disburses via PaymentProvider.payout() in that batch. Doctors see payout as pending until the next daily batch run.
- (decision) AD-11 [ADOPTED]: Response SLA clock pause/resume precision. Binds: Cases module (FR-10, FR-13; refines AD-8's daily breach job). Prevents: incorrect SLA-breach detection when a Case has spent time in More Info Requested (the clock must pause there, per FR-10, not keep running). Rule: Case tracks a cumulative paused-duration value (or explicit pause/resume timestamp pairs). Entering More Info Requested starts a pause interval; the Patient's next Document upload ends it and adds the interval length to the Case's cumulative paused duration. AD-8's daily breach job computes elapsed = (now - submittedAt) - cumulativePausedDuration and compares elapsed against the 5-day/120h threshold - only cases whose paused-adjusted elapsed time exceeds the threshold move to Refund Pending.
- (decision) AD-12 [ADOPTED]: Doctor specialty cardinality - multiple specialties per doctor. Binds: Doctors module data model, Cases module FR-9 queue filtering. Prevents: a single-specialty schema that would block a Doctor from registering multiple specialties, and ambiguity in how the Case queue matches a Case's condition to a Doctor. Rule: Doctor.specialties is a collection (many-to-many or array), not a single scalar field. FR-9's specialty-filtered queue shows a Case to a Doctor if the Case's mapped specialty is included in ANY of that Doctor's registered specialties. Resolves the PRD's open question on this point (§8) - PRD should be updated to reflect this resolution.

- (decision) AD-6 Rule tightened (Reviewer Gate finding C-3, adversarial): the atomic claim-if-still-unassigned operation is mechanized as optimistic locking via a Case.assignmentLockVersion column. Both the doctor self-claim path and the admin-reassign path go through one exported Cases-service function (e.g. assignCaseToDoctor(caseId, doctorId, expectedVersion)) that updates doctorId and increments assignmentLockVersion only if the passed version still matches; a version mismatch or already-assigned case returns a typed failure the caller must handle (retry on version mismatch, no retry on already-assigned). No separate ad hoc check-then-set implementation is permitted.
- (decision) AD-11 Rule tightened (Reviewer Gate finding C-2, adversarial): the 'cumulative duration value or timestamp pairs' choice is resolved to ONE mandatory shape - Case tracks an array of explicit pause/resume timestamp pairs (pausedAt, resumedAt|null). Elapsed-time-for-SLA-purposes is computed by exactly one exported function in the Cases module (not reimplemented per caller); any other module needing elapsed time (e.g. Payments for payout timing) must call that function rather than recompute from raw pause data.
- (decision) AD-13 [ADOPTED] (new, Reviewer Gate finding C-1, adversarial): Formal Case status state machine. Binds: Cases module (FR-7 through FR-13, all case lifecycle features), and any module reading/writing Case status (Admin, Payments, Doctors queue). Prevents: two independently-built modules inventing different state names/transitions since the Glossary and ADs only reference state names in prose. Rule: Cases module defines a single closed CaseStatus enum (Submitted, UnderReview, MoreInfoRequested, OpinionGiven, RefundPending, Refunded, Closed) and its legal transition graph in one place (e.g. domain/case-state-machine.ts); every other module imports this enum rather than redefining it. Admin reassignment (AD-5/AD-6) mutates doctorId without changing status. This enum is the single source of truth referenced by the Capability to Architecture Map for FR-7 through FR-13.
- (decision) AD-14 [ADOPTED] (new, Reviewer Gate finding H-1, adversarial): Document access control ownership. Binds: FR-14, StorageProvider usage across Cases/Payments/Admin. Prevents: access-control logic splitting across StorageProvider, service.ts, and route handlers with divergent rules for who can read a Document. Rule: access control for medical Documents is enforced at the owning module's service boundary (Cases service functions - Documents are semantically owned by Cases) - never inside StorageProvider and never re-implemented in a route handler. StorageProvider's interface takes no user/role context and is not responsible for authorization; it only stores/retrieves bytes for an already-authorized caller. Any other module needing a Document (e.g. Payments for audit) must call the Cases module's service function, which performs the patient-owns-case / doctor-assigned-to-case / admin-sees-all check before delegating to StorageProvider.
